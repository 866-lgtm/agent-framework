- MCPL content that context-manager won't store is refused where it arrives, and a deferred write that context-manager refuses no longer holds its agent's later writes. From context-manager 0.16.0, a write whose content doesn't match `ContentBlock` is refused with a `MalformedContentError` (context-manager #184). Before it, such content was stored as given, and a compile that read it could throw.
  - **The push and channel lanes** check content with context-manager's `malformedContentPlaces` before anything else. When it names any place, the message stores no row and queues no wake. A stderr line, `[push-event-refused]` or `[channel-incoming-refused]`, names the server, the channel where there is one, the event or message, and the places. A new trace, `mcpl:malformed-content-refused`, carries the same, with the places as `places`. Content the store mends, a `tool_use` whose input isn't an object, is stored as before.
  - **A deferred write that context-manager refuses as malformed is dropped at the drain** and logged, rather than queued again. Because it would be refused at every flush, it used to hold every later deferred write for its agent for good. Any other failure still holds the queue in order, as before. A `tool_use` dropped this way lets a `tool_result` queued behind it be stored alone. context-manager mends a `tool_use` whose input isn't an object, so it refuses one only when that input has no JSON form or the block itself is malformed.
