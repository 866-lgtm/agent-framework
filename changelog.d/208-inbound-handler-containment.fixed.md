- MCPL's inbound handlers are contained at one boundary, the framework's wiring, for every request and notification it handles (#186). The `channels/list`, `tools/observe` and `model/info` requests, and the `mcpl/manifestChanged` and `notifications/tools/list_changed` notifications, are newly contained: a throw or rejection of theirs is reported as the other handlers' are. The six requests whose handler failures 0.22.0 already answered (`push/event`, `inference/request`, `channels/register`, `channels/changed`, `channels/incoming` and `host/command`) go through the same boundary now. On a connection the framework wires, no handler's throw or rejection ends the host, and a rejection reason that can't be printed is reported as one that can.
  - **A request whose handler fails is answered `-32603` "Internal error",** where 0.22.x answered with the handler's own message, which can name internal paths and errors and goes to a server that may be a third party's. While the host is stopping, it's answered `-32000` "the host stopped while handling this request", without the handler's message that 0.22.x added after those words. The handler's error stays in the trace and on stderr. A request is answered this way when its handler fails before any reply bytes may have gone out: it attempted no reply, or its reply failed while encoding. A transport write that threw may have sent part of a reply, so it isn't followed by another. A notification gets no reply.
  - **Each failure emits a new trace, `mcpl:request-handler-error`, and a stderr line.** Its `error` is the handler's own error. A reply write that failed before it is `responseFailure`, and a reply the handler tried to send after one was already attempted is `refusedResponse` (a result, or an error with its code and message): refused, never written. `responseError` is the internal-error reply's own failure, which the stderr line prints too. `requestId` is the request's id when that is a string or a number. A failure of the Discord awareness accounting that a tools-list refresh waits on is global: it's reported as `mcpl:server-error` for every connection, as each is recycled.
  - **A request whose method isn't a string,** or isn't one the host handles, or whose event nothing on the host listens for, is answered `-32601` "Method not found", with a stderr line. A notification nobody handles is ignored.
  - **`mcpl/manifestChanged` and `notifications/tools/list_changed` sent as requests,** with an id, are answered with an empty result when the connection admits them, if something on the host listens for them, as the framework's wiring always does, and are handled as the notification is.
  - **Non-object JSON** (`null`, `42`, `"hi"`, `true`) is ignored before property access, in the handshake reader and in routing, as a non-JSON line already is. One such line from a server used to end the host (#217).
  - **A synchronous failure while dispatching an inbound message**, buffered plane flushes and a server's stderr lines included, is reported without interrupting later messages. Its `mcpl:server-error` names the event or method, the request id, and the cause.
  - **A response that can't be encoded** says why in its error (a BigInt, a circular structure, a throwing `toJSON`).
  - **A reply to a connection that has already closed** is dropped without a trace, on either transport, as before.
