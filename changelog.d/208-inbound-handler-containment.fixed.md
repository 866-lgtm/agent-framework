- MCPL's inbound handlers are contained at one boundary, the framework's wiring, for every request and notification it handles (#186). The `channels/list`, `tools/observe` and `model/info` requests and the `notifications/tools/list_changed` notification are newly contained: a throw or rejection of theirs is reported as the other handlers' are. `mcpl/manifestChanged` goes through the same boundary: a manifest fetch that fails is still caught and logged inside its handler, as in 0.22.x, and anything else its handler throws or rejects with is now reported as the others' are, where 0.22.x only logged it. The six requests whose handler failures 0.22.0 already answered (`push/event`, `inference/request`, `channels/register`, `channels/changed`, `channels/incoming` and `host/command`) go through the same boundary now. On a connection the framework wires, no handler's throw or rejection ends the host, and a rejection reason that can't be printed is reported as one that can.
  - **A request whose handler fails is answered `-32603` "Internal error",** where 0.22.x answered those six with the handler's own message, which can name internal paths and errors and goes to a server that may be a third party's. While the host is stopping, it's answered `-32000` "the host stopped while handling this request", without the handler's message that 0.22.x added after those words. The handler's error stays in the trace and on stderr. A request is answered this way when its handler fails before any reply bytes may have gone out: it attempted no reply, or its reply failed while encoding. A transport write that threw may have sent part of a reply, so it isn't followed by another. A notification gets no reply.
  - **Each failure emits a new trace, `mcpl:request-handler-error`, and a stderr line.** Its `error` is the handler's own error. A reply write that failed before it is `responseFailure`, and a reply the handler tried to send after one was already attempted is `refusedResponse` (a result, or an error with its code and message): refused, never written. `responseError` is the internal-error reply's own failure, which the stderr line prints too. `requestId` is the request's id when that is a number, and a string id bounded as the trace's other texts are. A request form of `mcpl/manifestChanged` or `notifications/tools/list_changed` has none, since it's answered as it's admitted and then handled as the notification is. A failure of the Discord awareness accounting that a tools-list refresh waits on is global: it's reported as `mcpl:server-error` for every connection, as each is recycled.
  - **A request whose method isn't a string,** or isn't one the host handles, or whose event nothing on the host listens for, is answered `-32601` "Method not found", with a stderr line. A notification nobody handles is ignored.
  - **`mcpl/manifestChanged` and `notifications/tools/list_changed` sent as requests,** with an id, are answered with an empty result when the connection admits them, which waits while their plane is paused, if something on the host listens for them, as the framework's wiring always does, and are handled as the notification is.
  - **Non-object JSON** (`null`, `42`, `"hi"`, `true`) is ignored before property access, in the handshake reader and in routing, as a non-JSON line already is. One such line from a server used to end the host (#217).
  - **An `initialize` error whose `message` has no string form,** such as `{"toString":1}`, refuses the connect, with `initialize error: [object Object]`. 0.22.x converted that message after the handshake had stopped listening and cleared its timeout, so the conversion's throw escaped as an uncaught exception, which ends a host that doesn't catch them, and the connect never settled. An `initialize` error's message is now bounded too, as the framework's other errors bound a server's text: control, format and line-separator characters become `?`, and it's cut at 200 code points.
  - **A synchronous failure while dispatching an inbound message**, buffered plane flushes and a server's stderr lines included, is reported without interrupting later messages. Its `mcpl:server-error` names the event or method, the request id, and the cause.
  - **A response that can't be encoded** says why in its error (a BigInt, a circular structure, a throwing `toJSON`).
  - **A reply to a connection that has already closed** is dropped without a trace, on either transport, as before.
