- A coalesced MCPL message with inline images is admitted like any other message (#266). Coalesced `channels/incoming` and `push/event` items, and render results, were checked against a 1 MiB budget on their serialized content, inline base64 images included, which uncoalesced messages never had. Any message with a sizeable screenshot was refused as `coalesce_invalid`, never stored and never woke the agent, and discord-mcpl tags every message create with `coalesce`. An incoming coalesced item's content now meets what an uncoalesced message's does: an array of objects with something visible in it (a retraction may be empty). A block the converters can't render, such as a video or an unknown type, becomes the same placeholder whether or not the message was coalesced. The converters of both lanes now take any object without throwing: a block's type, text, data, mimeType or uri that isn't a string is treated as absent, so a malformed block becomes a placeholder too (a text block, no text) instead of throwing in conversion, where the sender got no answer and a `channels/incoming` batch stopped before its later messages. A render result, which the host delivers in the occurrence's place, also has each block's shape checked, as RFC-006 §5.2 asks. The 4 KiB bound on `coalesce.data`, which the coalescer holds outside context, is unchanged.
  Every coalesce rejection is now visible on the host as well as on the wire, as a line and a `mcpl:channel-incoming-rejected` or `mcpl:push-event-rejected` trace with `field` and `detail`. A `[channel-incoming-rejected]` line names the server, channel, message id and failing field; a `[push-event-rejected]` line names the server, feature set, event id and failing field; each ends with the error's message. The reason follows the answer the sender got: `coalesce-invalid` when the item was the sender's to fix (malformed, or a push to a channel it isn't permitted or hasn't registered), `coalesce-failed` when the host itself failed (coalescing unavailable, the host stopping or unable to make an acceptance durable, or an internal error). A `channels/incoming` message for an unregistered channel now gets a line too (`reason=unknown-channel`), coalesced or not, and its trace carries the message id. A render result the host refuses gets a `[push-render-failed]` line naming the server, subject, event id and failing field, and the occurrence's own content is delivered instead. The wire answers are unchanged.
  Host log lines now print the values a server chose (channel, message and event ids, feature set and field names, a discarded method's name) in a form a server can't use to add a line that reads as another host record, or a word that reads as another field of the same line. That covers every `[channel-incoming-rejected]` and `[push-event-rejected]` line, the existing empty-content, duplicate and feature-set rejections included, and the `[channel-incoming-dropped]` and `[push-event-dropped]` backstops, the unread-message removal line, the `[routeSpeech]` delivery line, the feature-set disabled line and the discarded-method line. A plain token prints as before. Anything else prints as a JSON string with every space and invisible character escaped (a line break, a terminal escape, a bidi control, a default-ignorable character such as a Hangul filler or a variation selector), so `JSON.parse` of it gives back exactly what was sent, and a value that isn't a string prints as its JSON text. The feature-set rejection's reason, which names the feature set, is a field like any other: `reason="Unknown\u0020feature\u0020set:\u0020…"`. The host's own message at the end of a line is quoted the same way but keeps its plain spaces.
