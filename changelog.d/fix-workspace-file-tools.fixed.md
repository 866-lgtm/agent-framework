- The workspace's `edit` writes its replacement as given. It read `$&`, `$$`, `` $` `` and `$'` in `newString` as replacement patterns. It now refuses, changing nothing, three edits it used to report as successes:
  - an edit of a file that isn't valid UTF-8, where decoding and writing it back turned every invalid byte sequence in the file into U+FFFD;
  - an empty `oldString`, which matched between every character;
  - a lone UTF-16 surrogate in `oldString` or `newString`, which `write` now refuses in `content` too.
- Every workspace tool checks its input against its own schema before it does anything: required fields, strings, booleans, and whole numbers, with `read`'s `offset` and `limit` at least 1 and `grep`'s context lines at least 0. An edit missing `newString` wrote the word "undefined", and `replaceAll: "false"` counted as true. `read`'s `offset` and `limit`, and `grep`'s `contextBefore` and `contextAfter`, are typed `integer` in their schemas.
- A `write`, `edit` or `delete` that the workspace stored but couldn't finish still answers as an error. That covers one whose push to disk was refused, and one that failed after its change was stored. The answer now leads with the fact that the change is stored and mustn't be sent again, and its `data` carries `inChronicle: true`, as `writeBinary`'s does, with the `path`. Before, a refused push's answer began "Wrote to Chronicle", "Edited Chronicle" or "Removed from Chronicle", and a failure after the change was stored gave only the error. Either way, an edit sent again could apply twice.
- `read` counts the lines a file has: a final line end no longer starts an empty extra line, so "a\nb\n" is two lines, and an empty file has none. `grep` numbers lines the same way. An `offset` past the last line answers empty `content` with the file's `totalLines` and a note, and no `fromLine` or `toLine`, where before it claimed a range that ended before it began.
- An `edit` first takes in a change on disk the workspace hasn't seen, as a listing does, applies to that text, and says so in its receipt. Before, it edited the older stored copy, and on a mount that pushes, its push then failed as stale. Where the path's stored copy is a draft and disk changed too, the edit applies to the draft as before, and its answer names the conflict and the two ways out. `write` doesn't do this, since it replaces the whole file.
- `grep`'s refusal of an invalid pattern gives the parser's reason, and the workspace's refusals no longer begin with "Error: ". A push that disk's shape refuses says what's in the way and the way out: a directory at the path, or a file where the path needs a directory. Before, a directory's refusal offered `force`, which can't write there either, and a file in the way named no way out.
