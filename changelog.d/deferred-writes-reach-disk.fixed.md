- `quiesce()` now writes the queue of deferred context writes before it changes the host's mode, or fails, and a write of that queue that fails elsewhere is reported where an operator looks.
  - **A write deferred behind a turn still alive** before the host quiesced was held in memory only. `quiesce()` didn't write the queue, so when its drain timed out with that turn alive, a crash before the queue next changed lost the write. `quiesce()` now writes the queue first, before the host-mode record, on a first call and a repeat alike, and a write that fails rejects with the host's mode as it was.
  - **A queue over the cap** is refused by `quiesce()` too, with a `QuiesceBlockedError` that names the cap and both ways out: wait for the writes to land, or quiesce with `abandon: true`, then resume so they land, and quiesce again. A call with `abandon: true` goes on past the cap, since abandon is the call for a turn that won't end, and writes held for that turn land only once it does. The cap then raises the alert below. A turn the abandon can't end is listed as unabandonable, as before, and its writes land when it ends on its own.
  - **A write of the queue that fails elsewhere,** such as when a context write is deferred while quiesced, still keeps the queue in memory, since the write's source has already been answered, and the queue's next change writes it again. It used to be logged and nothing more. It now raises a `deferred-writes` ops alert at a run's first failure, and a line is logged when a write succeeds again, which ends the run. A queue over the cap counts as a failure, so it raises the same alert when it begins a run. The cap's line is logged the first time the cap is met in a run, where it used to be logged once a process. Like every ops alert, it reaches failures.log and the `ops:alert` trace each time, and the webhook, when one is configured, unless one of its kind was posted in the last 15 minutes.
  - **The cap is unchanged:** when the queue's JSON is longer than 4,194,304 characters, counted as the string's length, its record isn't written at all and keeps what it last held.
  - **Without a recovery file,** the store is the record, and the queue's write wasn't synced, so a crash could lose it. The store is now synced after the write, as it is for the host-mode record, and a sync that fails counts as a failed write. The write is already in the store by then, where a later sync can still put it on disk, so the queue stays mirrored from then on.
