- The workspace's `read` shows a file's text as it is, and says so. A line page shows a CRLF file's lines without the CR before each line feed, and leaves out a BOM. Its note says when the file has either, counting a mix of CRLF and LF ends. It also says when the file isn't valid UTF-8: each invalid byte sequence shows as U+FFFD, `edit` refuses the file, and `write` replaces it whole. Before, each line of a CRLF file ended in a CR, a BOM came first in the first line as U+FEFF, and invalid bytes showed as U+FFFD with no word. A character page still reads the stored text as it is, BOM and CRs included, and the tool's description now says so.
- A line over 2,000 characters is cut, with how many characters follow and the `offsetChars` that reads them. Before, a line page showed every line whole, however long.
- A `read` page stops before its result would pass `resultMaxChars`, the most of it the framework stores whole. For a model's call that's its agent's inline cap, 24,000 characters by default, and a call that carries none gets 24,000 too. Its note says where to continue: the `offset` after its last line, or for a character page the `offsetChars` it also gives as `nextOffsetChars`. Where even a page's first line would pass the limit, that line is cut shorter, at the most the page has room for. Where a page's last line is cut, its note names the `offsetChars` where that line's rest starts before the next line's `offset`. A page always moves on, so where its own fields (the path and its notes) and the least it can show pass a small limit, it passes the limit: at 1,000 characters, only a path of about 130 characters or more beside every note a read can carry does that, or one of about 700 with none. Before, a page of up to 2,000 lines, or of `limitChars` characters, went out whole, and the framework wrote what passed the limit to a file, cut mid-JSON. A caller that pages 2,000 lines at a time and starts the next page at line 2,001 now starts where the note says. A running `code_execution` script's call has a limit of 5,000,000 characters, so its pages still stop at 2,000 lines or `limitChars`, unless a page would pass that.
- The workspace's `grep` leaves out a CR before a line feed, for matching as well as display, as ripgrep's `--crlf` mode does, so `foo$` finds a CRLF file's line too. A match's text and context are the lines as `read` shows them, a BOM isn't part of the first line, and a file with CRLF ends says so in its result's `lineEndings` (`CRLF`, or `mixed`). Before, a CRLF file's lines ended in a CR, so `foo$` missed them and a match's text copied into an edit carried the CR. A pattern written to find the CR of a CRLF line end no longer matches; a CR that doesn't come before a line feed is still part of its line.
- The workspace's `read` first takes in a change on disk to a file the workspace holds, as a listing and an `edit` do, and shows that text. Its note says so when disk's copy had changed since the workspace last agreed with it. It also says when disk's copy couldn't be checked, or disk has none and nothing records whether it was deleted there, so it shows the workspace's copy. A file disk deleted answers that disk deleted it and the deletion was taken in, and a file disk made binary or too large answers that it's on disk but not stored. Where the path's stored copy is a draft and disk changed or deleted it too, the read shows the draft, and its note names the conflict and both ways to settle it: for a deletion, a sync of the path takes it and removes the workspace's copy. Before, a read of a path the workspace held didn't look at disk, so it could show a copy another writer had since changed; a path it didn't hold was observed, as now.
- The `read` and `grep` tool descriptions changed, so the first request after the upgrade that carries the workspace's tools misses the prompt cache from its tool block on.
