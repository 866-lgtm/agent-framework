- Server and transport text the framework records has the server's configured credentials replaced, in both engines: connection traces, console lines, stderr traces, the ops alert (and so `logs/failures.log` and the webhook), a tool call's failure as its caller and the model get it, and the `tool:failed` trace's message and stack. The credentials are those the configuration holds: from the url, credential-like path segments and query names, credential-shaped or credential-named query values (each as written and decoded), every non-empty parameter as its whole `name=value`, and a `ws://` url's username and password; the static `token`, raw and as a url carries it, percent- or form-encoded; and a stdio server's `env` values whose names have a part ending in a credential word, singular or plural, with any digits after it (`GITHUB_TOKEN`, `API_KEYS`, `PGPASSWORD`, `DB_PASS`, `AUTHORIZATION`, `SESSION_COOKIE`, `TOKEN2`), raw and percent-encoded. A stdio server's command-line arguments are not derived. A string replaced on its own has at least eight characters, since a shorter one can't be told from ordinary text, and is replaced wherever it occurs. Every query parameter is also replaced as its whole `name=value`, only where no letter or digit adjoins the pair (so `v=2` leaves `dev=2` alone); a short value goes only that way. A connection's event records use a redactor built once for it, and an operation's records one built when the operation begins, so a server removed, or replaced by a restart, while the operation waits doesn't change what they replace. A 401 or 403's response body is left out of the request error's data; where the HTTP client builds the error's message from the body, as it does for most statuses, the message is redacted like any record. A token an access provider fetches, and credentials the configuration doesn't hold, are outside this. JSON-RPC answers, and the error a host's own connect raises, pass as they are.
