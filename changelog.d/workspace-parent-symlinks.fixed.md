- A workspace mount that doesn't follow symlinks (`followSymlinks` unset or false) now follows none among the directories on a path's way either. Before, a symlinked directory pointing inside the mount was followed, so the workspace acted on a file under another path than the one it named: a materialize deleted, created or overwrote the file behind the link, and a sync took that file's bytes in. Such a path is now refused wherever the link leads, naming the link: for a link to a directory inside the mount, with its target and that the mount's host can set `followSymlinks: true`, and for one leading outside the mount, saying so. On such a mount, reads through an inside directory link stop, a listing of the directory a link stands at says so instead of walking it, and `readFileFromDisk` and `read_image` answer `symlink` where they answered `escape` for a directory link leading out of the mount. A mount root that is itself a symlink is still the root, and a mount that follows symlinks keeps following them while they stay inside it.
