- A workspace mount with more files than one walk takes is now covered by repeated syncs and scans (#272). Each mount sets its cap with `walkCap`, a positive integer that defaults to 5000; any other value is refused when the module is created, naming the mount. A bare `sync`, a `sync` of a directory, an agent-action scan, or a watched mount's first scan that reaches the cap lists what it didn't reach under `incomplete`, and the next one of the same scope resumes after the last file it took, then wraps to the start. The place is kept with the mount's disk evidence, so a restart resumes there too. Before, every walk stopped at 5000 files in `readdir` order, so the files past the cap were never scanned, and a change to one reached the workspace only through a `sync` of its path. A listing (`ls`, `glob`, `grep`) still takes up to the cap from its scope's start.
  - A walk takes each directory's files by name, then its subdirectories by name, so the files past the cap are the same from one walk to the next.
  - Each directory's listing is read whole, so a file deleted on disk is seen wherever the walk lists, past the cap included. Before, a directory holding more files than the cap never proved a deletion.
  - The `sync` tool's description says this, so the first request after the upgrade that carries the workspace's tools misses the prompt cache from its tool block on.
  - Going back to 0.22: the place is kept in an entry 0.22 doesn't know and leaves alone, so its walks start at the top again.
