- Two channels whose ids differ only in characters a conversation fork's name can't hold, such as `foo bar` and `foo-bar`, no longer get forks of one name. The name was the channel id with each run of characters other than letters, digits, `_` and `-` replaced by `-`, so both channels' first forks were `conversation-foo-bar-g1`. In one process, the second channel's spawn failed ("already registered or reserved") on every message, and its messages reached no agent. After a restart, its fork opened the first channel's namespace, wasn't seeded because that namespace already held history, and carried on as the first channel's conversation, which then went to the model in the second channel's turns. A fork's name is now `<prefix>-<readable>-g<generation>-<hash>`, such as `conversation-discord-123-456-g2-` and 16 hex digits for discord-mcpl's channel `discord:123:456`. The readable part is that sanitized id cut to 48 characters, and the hash is the first 16 hex digits of a SHA-256 of the server and channel ids. Traces, logs, the fork's namespace (`conversations/<name>`) and the fork's own participant name in its context carry the new form. A pattern over a name's leading part, such as `conversation-slack-C1-g*` in a server's `toolLifecycle` narrowing by `conversations`, still matches it. Bindings aren't stored and the generation counters keep their keys, so nothing stored changes: after the upgrade, each channel's next fork takes the next generation under the new form. `IncomingMessageFacts` gains an optional `serverId`, which the framework passes; a direct `ConversationRouter.route()` call without it gets a name hashed from the channel id alone.
