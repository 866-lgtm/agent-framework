- A mount nested in another is now that mount's directory wherever disk puts it, not only where the outer mount's paths name it as written. A root configured through a symlink, or beneath one, is nested where its real path lies; before, it wasn't nested at all, and the outer mount took in and read the inner mount's files. Each mount's root is resolved for this once, synchronously, when the module is constructed. On a mount that follows symlinks, a path that reaches a nested mount's directory through a link is now refused as one written into it: the file tools answer `"work/l/x.txt" leads into mount "inner", nested in mount "work", which neither reads nor writes it: use "inner/sub/x.txt".`, a sync or a materialize leaves it with `"work/l" leads into mount "inner", nested in mount "work": use "inner/sub" in its place`, and `readFileFromDisk` refuses it with the code `other_mount`. Before, the outer mount read, took in, wrote and unlinked the inner mount's files through such a link. On a mount that doesn't follow symlinks, a `write`, `edit` or `delete` through a link into a nested mount's directory is now refused before anything is stored, with the link's own refusal; it used to store a change that no push could write.
- A mount configured with a relative root written with `./`, such as `./m`, now hears its watcher; it heard no change on disk.
