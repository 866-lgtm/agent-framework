- The workspace has an `edit_many` tool: several exact edits, in one file or across files of one mount, stored all or none. Each edit gives `path`, `oldString`, `newString` and `occurrences`, how many times `oldString` must occur (1 when left out), and every occurrence is replaced. Each edit is matched in its file as the call reads it, never in another edit's result, so the list's order doesn't matter, and two edits' matches may touch but not overlap. Matching is `edit`'s. Its input is checked item by item, as every workspace tool's input is checked.
  - Any problem stores nothing. The refusal names every problem it finds, in edit order, each by its edit's number from 1: a miss with its closest region, a count that differs with the lines that matched, edits whose matches overlap, an edit's own refused input, a path no mount holds, a read-only mount, a generated file, a file it can't edit, and edits naming files in more than one mount.
  - Every path is first settled with disk, in one pass, as `edit` settles its one. Then every file is read and planned, and every entry set, with nothing awaited between, so no other call, pass or branch change moves the tree between a file's read and its set.
  - On a mount with `autoMaterialize`, disk can still refuse a file once every edit is stored. The answer then leads with the fact that every edit is stored, so the call mustn't be sent again, and names each file disk refused, with its push's reason. A call that fails after storing some files names the files stored and those not.
  - The answer gives each file's `size`, `replacements`, `edits` and `note`, and `changed`, each edit's first changed region, numbered. It is held to the call's `resultMaxChars` as `edit`'s is: past it, regions are named by their lines, and files are counted rather than listed.
