- A workspace mount can name the files it holds with `include`, in the same pattern forms as `ignore`, read for files: a name or an extension glob covers a file by its own name, at any depth, and a `dir/**` glob covers what lies beneath that directory, and not a file named like it. Unlike `ignore`, a pattern that matches a directory's name covers nothing beneath it, since each file is covered by its own name: `include: ["gate.json"]` holds every file named `gate.json`, and no other file beneath a directory of that name. It's the mount's boundary. A file or link it doesn't cover is outside the mount: a walk passes over it and counts it under `passedOver` as "outside the mount's include", a change the watcher reports there is dropped, and `materializeMount` and `materialize` never write it back, even when the workspace's history holds it from before the include (a `materialize` naming a directory inside the mount counts each such entry beneath it under `passedOver`, with that reason and without its path, so no tool names a file outside the include, beyond echoing a path it was given). Every tool refuses a path with a `..` segment on such a mount, whatever it reaches, before it looks the path up, saying to give the path from the mount's root with no `..` in it. Text a host registers for a path with `registerGeneratedTextFile` is the exception: it's served there whatever the include says, every spelling that resolves to its path reads it, a `..` one included, and none writes it. On a disk that folds names, a spelling in another case isn't its path, and reaches whatever file disk has there. `read`, `read_image`, `write`, `edit`, `delete`, `readBinary`, `writeBinary`, `readBinaryFromDisk` and `readFileFromDisk` refuse any path it doesn't cover, a directory's included, saying it's outside the mount's include (`readFileFromDisk`'s error code is `outside_include`, for a `..` path too), and `resolveAbsolutePath` returns null for one; the mount's root is inside when it's named without a `..`. A path in a nested mount's directory is that mount's, whatever this mount's include covers: every tool gives the answer that names the mount holding it and the path to use there, as on a mount without an include. A path with a `..` segment is refused before that. A `sync`, `materialize`, `grep`, `glob` or `ls` that names a path the include doesn't cover takes it as a directory, its scope, exactly where a listing names one: where disk has a directory reached from the mount's root through directories, with no link among them, or the workspace's history holds an entry beneath it that the include covers. The one exception is a directory `ignore` covers, which a listing passes over and which is still a scope when it's named, as a sync that names it takes in what's there. Where covered history makes a name a scope and disk has since put a link there, a mount that doesn't follow symlinks refuses the link, as it refuses any link on a path's way, and on a mount that does, a pass of that scope follows the link, so its answer shows whether the link leads out of the mount. A link's refusal names an inside target only where a tool could name it: a directory, or a file the include covers. Where the target lies in a nested mount's directory, that mount's own include decides, and `readFileFromDisk` answers `other_mount` only where the refusal names that mount, and `parent_symlink` otherwise. Each refuses any other path the include doesn't cover the same way, so a name outside the include gets the same answer whether a file is there, on disk or in the workspace's history, or not. A covered path is a file to a `sync`, `materialize` or `grep` when disk or the workspace's history has a file there, and otherwise a directory, and a `glob` takes its path as a directory. Beneath a directory, each passes over what the include doesn't cover. Directories are walked unless `ignore` covers them, and no link the walk meets is walked, so an `ls` that isn't recursive names each directory directly beneath its path that disk has, whether or not anything beneath it is covered, and each that a covered entry in the workspace's history implies; the files a listing shows are only those the include covers. `ignore` still applies to what `include` covers. On a disk that folds names, a path is judged as disk spells it, as the walk judges what it lists, so a covered name whose file disk spells otherwise, such as `gate.json` where disk has `GATE.JSON`, is outside the mount, though `resolveAbsolutePath`, which is synchronous, judges the include on the path as given: it returns the path that reaches that file, and null for a covered file named in another case. It takes a nested mount's directory in any spelling disk folds to it as that mount's. A refusal shows the path as given, and past a nested mount's directory an answer shows the rest of the path as given, so neither tells whether a file is there. Left out, nothing changes. An empty list, an entry that isn't a string, or a pattern the matcher can't read (a path with `/` that isn't a `dir/**` glob, a `*` anywhere but a leading `*.`, or an empty, `.` or `..` segment), is refused when the module is created, naming the mount and the pattern. Any other pattern is a file name, matched literally. So connectome-host's `_config` mount, which versions the host's config files, can hold only those: a file saved beside them, such as a kept `gate.json.unreadable-<suffix>` copy, stays out of its history and is never written back (connectome-host #278).
  - History from before the include stays as it was: no pass decides an entry outside it, a `materialize` of the whole mount leaves a deletion or conflict held outside it alone (one that names a directory inside the mount counts those beneath it under `passedOver`), the mount's `status` counts only what's inside, and a listing shows no directory that only such history holds.
  - The framework keeps its own files (`tool-results/`, `refs/`, `background-scripts/`) in the first read-write mount without an include, and a setup whose only writable mount has one is treated as having none. What it kept in a mount before the mount had an include is outside the mount once it has one, unless the include covers it, so a `read` of a path an earlier spill note or reference gave is refused.
